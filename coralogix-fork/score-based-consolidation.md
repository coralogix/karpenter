# Score-based consolidation

This fork adds an alternate compaction method for NodePools that opt in via annotation. It evaluates non-empty active nodes as possible compaction sources and ranks feasible moves by their evaluated score.

The annotation opts a NodePool into this behavior. Score-based consolidation applies only to dynamic NodePools whose `consolidationPolicy` is `WhenEmptyOrUnderutilized`. In score-based mode, `consolidateAfter` is ignored entirely, including `Never`. Removing the score-based annotation returns the pool to upstream consolidation behavior. An annotated pool with another policy does not run score-based consolidation; remove the annotation to use upstream consolidation for that pool.

## Configuration

Add the annotation to a `NodePool`:

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: example
  annotations:
    karpenter.coralogix.net/score-based-consolidation: ""
spec:
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 0s # Required by the NodePool schema; ignored by score-based mode
```

| Annotation | Meaning |
|------------|---------|
| `karpenter.coralogix.net/score-based-consolidation` | Opt the NodePool into score-based consolidation (presence of the key is sufficient; value is ignored) |
| `karpenter.coralogix.net/reclamation-interval` | Minimum Go duration between successful empty-node reclamations; defaults to `1m`. Invalid or non-positive values use the default. |
| `karpenter.coralogix.net/utilisation-weight` | Dimensionless weight for the additive per-source CPU slack ratio; defaults to `1`. Invalid or non-positive values use the default. |
| `karpenter.coralogix.net/memory-surplus` | Extra allocatable memory per CPU relative to the non-DaemonSet workload memory/CPU request ratio; defaults to `0.2` (20% memory surplus). Invalid, negative, NaN, and infinite values use the default. |
| `karpenter.coralogix.net/memory-balance-weight` | Dimensionless weight for the memory-balance correction; defaults to `0`, which disables memory-aware scoring. Invalid, negative, NaN, and infinite values use the default. |
| `karpenter.coralogix.net/instance-type-concentration-threshold` | Per-pool instance-type node-share threshold; defaults to `0.5`. Valid values are finite fractions in `[0, 1)`. |
| `karpenter.coralogix.net/instance-type-concentration-weight` | Dimensionless bonus added per source node whose instance type is above the threshold; defaults to `0`, which disables the term. Valid values are finite and non-negative. |

The utilization and memory-balance weights now have dimensionless semantics. Existing values may need recalibration; there is no automatic unit conversion because price normalization varies by NodePool and capacity type.

Memory-aware scoring is opt-in per NodePool by setting a positive `memory-balance-weight`. The weight `10` below is illustrative only and is not a calibrated recommendation:

```yaml
metadata:
  annotations:
    karpenter.coralogix.net/score-based-consolidation: ""
    karpenter.coralogix.net/memory-surplus: "0.2"
    karpenter.coralogix.net/memory-balance-weight: "10"
    karpenter.coralogix.net/instance-type-concentration-threshold: "0.5"
    karpenter.coralogix.net/instance-type-concentration-weight: "1"
```

Instance-type concentration scoring is opt-in through a positive weight. For each source node, it adds the configured weight when that node's type share is strictly greater than the threshold; exactly-at-threshold types receive no bonus. The share is that type's node count divided by the count of all initialized, non-deleting managed nodes in the NodePool. Standby, activating, and otherwise ineligible nodes remain in this inventory. Capacity types and zones are combined, and a missing instance-type label remains in the denominator without increasing any type's count. The term applies to source nodes only and adds once per qualifying source in single-node, pair, and batch moves.

Invalid, negative, non-finite, or out-of-range annotation values fall back to the defaults. The bonus is based on the source node's type concentration only; it does not adjust for the replacement node's instance type.

## Behavior

- Eligible annotated dynamic NodePools use three methods: `ScoreBasedStandby` after upstream `Emptiness`, `ScoreBasedReclamation` after standby marking, and `ScoreBasedConsolidation` after multi-node consolidation and before single-node consolidation. Upstream emptiness, multi-node, and single-node methods continue to skip annotated pools.
- The `WhenEmptyOrUnderutilized` policy and dynamic NodePool requirement still apply, but `consolidateAfter` does not gate standby marking, score-based reclamation, or score-based compaction. Its value, including `Never`, has no effect while the score-based annotation is present.
- For an initialized NodeClaim in an annotated dynamic `WhenEmptyOrUnderutilized` pool, the `Consolidatable` condition is set without waiting for `consolidateAfter`. This condition indicates timing eligibility; it does not guarantee that a feasible, profitable move exists or that budgets and pacing allow one now.
- `ScoreBasedStandby` marks all eligible empty active nodes in configured pools as standby in its own `StandbyAction`. It runs without the consolidation TTL, budgets, or underutilized pace limits. It first taints the Node, then checks live occupancy; if a scheduler using a stale Node cache bound a workload during the transition, it clears the marker and taint and leaves the node active. Disruption controller cleanup also periodically checks live occupancy and restores occupied standby nodes to active. Standby marking has a dedicated summary log (`marked empty nodes as standby`), a Normal `Standby` event, and `karpenter_nodes_standby_marked_total{nodepool}`; it does not emit evacuation, consolidation-candidate, or deletion metrics. When it starts a command, the normal method boundary ends that controller pass and schedules a retry from the top.
- Reclamation runs after standby marking and before drift and multi-node consolidation, so it can act without waiting for their calculations. It selects only nodes that have both the standby marker and taint, checks live occupancy and activation state, and deletes with the validated NodeClaim UID and resource version. It has no consolidation TTL. When it starts a command, the normal method boundary ends that controller pass and schedules a retry from the top; score-based compaction is reconsidered on that retry, subject to methods earlier in the order. When reclamation finds no command, the controller continues through the remaining methods in the same pass.
- Dynamic and static drift continue to use the standard drift methods and `Drifted` disruption budgets. The optional underutilized pace annotations also limit non-empty drift candidates and share their per-NodePool cooldown with consolidation.
- `ScoreBasedConsolidation` handles only non-empty active compaction candidates. It reports disruption reason `Underutilized` and honors the `Underutilized` NodePool disruption budget and optional underutilized pacing. Empty-node reclamation is handled by its own method and reports `Empty`; it is exempt from NodePool disruption budgets and underutilized pacing.
- Each search shuffles candidate order before evaluating all single-node move sets in parallel with up to `runtime.GOMAXPROCS` workers. Valid single-node commands and 2→1 pair commands are ranked by normalized cost contribution, additive utilization contribution, memory-balance correction, and instance-type concentration bonus. For each source node `i`, `aᵢ = sourcePriceᵢ / (allocatableCPUᵢ × baselinePricePerCPU(NodePoolᵢ, capacityTypeᵢ))`; the baseline is total hourly price divided by total allocatable CPU for all relevant initialized active managed nodes in that pool and capacity type. The normalized cost contribution is `f × Σaᵢ`, where `f = (sum source prices − replacement price) / sum source prices`. Replacement pricing uses the existing score-based replacement-price estimate and is not separately normalized. The utilization contribution is the sum, over source nodes, of the dimensionless utilization weight (default `1`) times each node's unallocated CPU divided by its allocatable CPU. The concentration bonus is the sum of the configured weight for each source whose instance-type share exceeds its pool threshold.
- Cost baselines use the same immutable scheduling snapshot as move evaluation and include fleet nodes even when they are not disruption candidates. Deleting, uninitialized, standby, activating, and non-managed nodes are excluded. Offering prices are resolved by instance type, capacity type, and zone. A known zero-price source contributes zero; a missing source price or an unknown or non-positive baseline for a positive-price source invalidates that move. Common price scaling leaves the normalized cost contribution unchanged. The raw positive-dollar-savings gate remains in force.
- Each search takes one owned copy of the node snapshot used by the scheduling simulator and uses it for both price and memory baselines. For each configured pool, the memory baseline includes every initialized, active managed node in that snapshot, including nodes that were not search candidates. Allocatable CPU and memory, and pod requests, have DaemonSet requests subtracted. Deleting, uninitialized, standby, and activating nodes are excluded. A pool with an unknown or zero CPU/memory ratio is left uncorrected.
- Let `q` be pool allocatable memory per CPU and `t = (1 + memory-surplus) × non-DaemonSet requested memory / non-DaemonSet requested CPU`. The configured surplus is extra memory per CPU relative to the workload's requested memory/CPU ratio. Pressure is zero when `q/t` is between `0.95` and `1.05`, inclusive; outside that deadband it is `clamp(log2(q/t), -1, 1)`. Thus a ratio at or below one-half saturates at `-1`, and a ratio at or above two saturates at `+1`.
- For a move, the pool-local shape delta is removed `(memory/q - CPU)` minus added `(memory/q - CPU)`. The normalized delta is that pool's delta divided by total CPU removed by the command and clamped to `[-1, 1]`. Its correction is `memory-balance-weight × pressure × normalized-delta × source-node-count`; corrections from affected pools are added to the base score. The source-node-count multiplier keeps a joint correction on the same per-source additive scale as the cost and utilization terms. Per-pool logs retain the unmultiplied normalized delta and report the multiplied contribution and source-node count. Replacement capacity is assessed across every compatible available offering, after subtracting the DaemonSet overhead for that instance type. The scorer chooses the least favorable pressure-weighted option so one optimistic offering cannot create a phantom benefit. Standby nodes activated by the command count as added capacity. An unknown source or destination pool ratio, unknown source or destination shape, or unnormalizable addition makes the total memory correction zero.
- The raw positive-dollar-savings gate remains in force. A move is rejected when its normalized total score is non-finite or non-positive, whether or not memory or concentration scoring is enabled. Changing either memory annotation or either concentration annotation invalidates the score-based consolidation cache so the new setting is evaluated on the next pass. With the default memory and concentration weights of zero, their corrections are zero; normalized cost scoring remains active.
- When at least one positive-savings single-node move is feasible, the search grows batches only from successful single-node moves that need no replacement. It starts from up to three highest-scoring distinct moves, jointly simulates each proposed addition, and retains only batches that also need no replacement. Because a no-replacement batch has `f = 1`, its normalized cost and utilization contributions are additive across its source nodes. The batch applies one joint memory correction computed from the full batch shape. Budgets and per-command pacing caps apply to the aggregate batch.
- When the completed single-node search finds no positive-savings move, the search samples up to 256 unique node pairs and accepts only pairs that replace the two source nodes with exactly one node. Pair sampling favors low CPU-utilization candidates while retaining a nonzero chance for higher-utilization candidates. Pair spaces with at most 256 combinations are searched exhaustively; larger spaces use the bounded weighted sample. A timed-out single-node search does not start the pair search.
- After search completes or reaches its deadline, the method keeps up to 10 commands by score and reserves fallback entries for the best singleton, another singleton with lower overlap when available, and the smallest feasible batch. The controller then waits for any remaining consolidation TTL time since the pass started and executes the first command that still passes final validation. Each pass has a 15-second timeout (single-node consolidation keeps the upstream 3-minute timeout).
- **Temporary (experimental):** `ExperimentalReclamationRemoveAllEmptyImmediately` in `score_based_reclamation.go` is currently `true`. While enabled, every pass reclaims all eligible standby nodes in each configured pool (no half-batch or interval gate). Revert to interval + half-batch pacing when reclamation policy is finalized.
- Standby marking runs for all eligible empty active nodes in annotated dynamic NodePools and does not wait for reclamation to become due. Reclamation counts only empty, non-terminating nodes with both the standby marker and taint. When experimental immediate reclamation is off, it is due on the first pass and again after the configured interval following a successful deletion. The default interval is one minute; the NodePool annotation can override it. A due pass reclaims up to half rounded up (or all eligible standby nodes while the experimental flag is on), preferring the highest instance price per vCPU. NodePool disruption budgets and underutilized pacing do not limit standby marking or reclamation. DaemonSet pods, terminal pods, and Node-owned mirror pods do not block emptiness; live nonterminal terminating workload pods do. Both the standby transition and reclamation skip the consolidation TTL.
- The controller stores the last successful reclamation time in the NodePool annotation `karpenter.coralogix.net/last-reclamation` using RFC3339Nano. This metadata is updated only after an individual NodeClaim deletion succeeds, so a partially completed batch still records its progress.
- Reclamation exposes the counter `karpenter_voluntary_disruption_score_based_reclamation_node_removals_total` labeled by `nodepool`, incremented after each successful deletion callback and timestamp update. Batch selection details are logged at verbosity 1; a fully completed batch produces one structured Info log with reclamation counts grouped by NodePool. These logs omit node and pod names. Score-based search details are available at verbosity 1, with evaluation failures counted by `karpenter_voluntary_disruption_score_based_move_set_evaluation_errors_total` and summarized once per search with the first error.
- Score-based compaction emits one Info summary whenever an error-free pass returns no command. Its reason distinguishes a consolidated cluster, no eligible or filtered candidates, budget or pace filtering, a timed-out search, no positive or feasible moves, and top moves rejected during validation. The summary includes candidate and evaluation counts, no-op, non-positive-savings, and non-positive-score counts, validation attempts, and sorted NodePool names blocked by budgets or pace limits, including when other candidates were evaluated. When candidate discovery returns none, the controller logs the no-eligible-candidates summary before skipping command computation. A selected-move summary groups the actual search path, simulated decision, source-node identities, instance and capacity types, per-node costs and scores, ranking and cost breakdown, per-NodePool/capacity-type price baselines, normalized cost contribution and savings fraction, search counts, validation rank, and each affected pool's memory/CPU ratio, target ratio, pressure, normalized move delta, weight, source-node-count multiplier, and correction. The `singleNodeMoveScore` is the original singleton evaluation score for each source node in a batch; pair moves omit it because no singleton succeeded. The `memory_balance_snapshot` span is emitted once per search and reports snapshot node/pool counts and valid pool ratios when memory scoring is enabled; it uses the snapshot already taken for price normalization. Estimated hourly replacement cost follows the same cheapest-offering input used by move scoring and does not identify which instance type will launch.
- Score-based compaction emits `ConsolidationCandidate` events on a Node and NodeClaim only for the move selected after validation. A move rejected during final validation emits `ConsolidationRejected`, including when a lower-ranked move is selected instead. A feasible simulated move with no positive estimated savings emits a deduplicated `Unconsolidatable` event. Existing disruption and scheduling blockers continue to emit their usual events. An effective `Underutilized` budget exhausted by in-flight disruptions, or a configured pace limit blocking compaction, emits a deduplicated `DisruptionBlocked` event on the NodePool. Lower-ranked feasible moves do not receive blocker events because they remain eligible for a later pass.
- Evacuation records one terminal log per command and exposes `karpenter_voluntary_disruption_evacuation_commands_total{outcome,reason}` plus `karpenter_voluntary_disruption_evacuation_duration_seconds{reason}`. Successful evacuation also increments `karpenter_nodeclaims_evacuated_total{reason,nodepool,capacity_type}` once per distinct source NodeClaim handed off to standby; failed evacuations do not increment it. This complements `karpenter_nodeclaims_disrupted_total`, which counts NodeClaim deletions, while the command counter remains one count per evacuation command. Standby activation records one log when the taint is removed and increments `karpenter_nodes_standby_activated_total{nodepool,instance_type,source}` once per successful activation. `source` identifies the demand path (`provisioning` or `compaction`); `recovery` identifies an interrupted activation whose original source was not recorded. A missing instance-type label is reported as `unknown`.
- `karpenter_nodepools_empty_nodes{nodepool,state}` gauges the current number of empty nodes in each NodePool using score-based reclamation, including when reclamation is not due. `state` is `standby` for nodes with both the persistent standby marker and standby taint, and `other` for all remaining empty nodes. Both states are reported at zero when applicable. The gauge uses reclamation's live emptiness definition and includes empty nodes that cannot currently be reclaimed. Its series disappear when a NodePool leaves score-based reclamation or is deleted.
- Standby NodeClaims carry the `karpenter.coralogix.net/standby` annotation and their Nodes carry a matching `NoSchedule` taint. Empty active nodes enter standby through the dedicated standby action. If a stale scheduler cache binds a workload during the transition, the transition check or periodic disruption cleanup clears the marker and taint and returns the node to active state. Orphan standby taints without live standby or activation markers are also cleared during cleanup. Reclamation can delete an empty standby node when its pool is due. Normal compaction considers only active nodes with reschedulable workload and excludes standby and activating nodes. A terminating-only workload node stays active until that pod leaves or becomes terminal, then standby marking or reclamation owns it. Nodes reserved for activation with the `standby-activating` annotation are excluded from reclamation. The final reclamation check verifies marker, taint, activation, and live emptiness, then deletes using the validated NodeClaim UID and resource version. A scheduler bind after the final occupancy check can still race with deletion; Kubernetes has no atomic scheduler-binding/NodeClaim-delete barrier, and any bound pod then follows the normal node termination drain path.
- Optional underutilized pace annotations (`max-underutilized-node-disruptions-per-minute`, `max-underutilized-nodes-per-consolidation`) apply to non-empty score-based compaction, single- and multi-node consolidation, and drift. Empty-node reclamation reports `Empty` and is not paced, matching upstream `Emptiness` behavior.

### Selected-move log details

The `score-based consolidation move selected` Info record captures each source node's price, allocatable CPU, requested CPU used by the scorer, its NodePool/capacity-type price baseline, normalized source cost, cost contribution, CPU slack fraction, effective utilization weight, and utilization contribution during evaluation. Each source also reports its instance type, pool node count, instance-type node count, share, threshold, weight, eligibility, and bonus contribution. The aggregate concentration breakdown groups source counts and contributions by NodePool and instance type. The move score reports normalized cost, utilization, joint memory correction, concentration correction, and total ranking score. `singleNodeMoveScore` retains its standalone singleton-evaluation meaning when it appears on a batch source.

Joint memory details are grouped by NodePool. Each pool reports its effective memory surplus and weight, capacity and target memory-per-CPU ratios, pressure, normalized delta, source-node multiplier, contribution, and aggregate removed and added shapes. Memory status is `disabled`, `applied`, or `unavailable`; unavailable status includes a reason and contributes exactly zero. Replacement shapes are the scorer's conservatively assessed worst-case compatible offering after DaemonSet overhead. This assessment describes scoring input and does not predict which instance type will launch. Activated standby nodes are included as measured allocatable shapes.

The event also includes up to three other retained evaluated move sets with source node names, search path, simulated decision, savings, compact score terms, and validation status. A failed move includes its categorized validation reason; later entries show `not_attempted`. Search records expose `timedOut`; retained moves describe only evaluations completed and kept by the bounded search, so the record makes no claim that the alternatives are exhaustive or globally optimal.

## Rollback to upstream

Rolling back the controller to upstream Karpenter is safe:

- The annotation remains valid Kubernetes metadata.
- Upstream ignores the annotation and does not run score-based consolidation.
- Annotated NodePools resume standard emptiness and underutilized consolidation behavior.
- No manifest or CRD changes are required to roll back.

Removing the annotation from an individual NodePool also returns that pool to the upstream consolidation methods.
