# Move search and selection

Status: accepted

The decision is recorded in `.scratch/score-based-consolidation/issues/01-search-and-selection.md` (Comments).

**Amendment (2026-11-20):** Ticket 01_2 (pacing before simulation) moved the whole-command pacing check before compute, so a move it rejects costs no simulation. The decision is recorded in `.scratch/score-based-consolidation/issues/01_2-pacing-before-simulation.md` (Comments).

**Amendment (2026-11-20):** Batch moves are grown after validation instead of during the search, and only one move runs per pass. The reserved place for the best single-node move among the kept moves is dropped. The decisions are recorded in `.scratch/score-based-consolidation/issues/04-batch-moves.md` (Comments).

**Amendment (2026-11-20, pair moves):** Pair moves run when no single-node move is feasible, only admissible pairs count toward the pair limit, sampling is bounded by a draw limit, validation applies the generic rule to pairs, and a sampled pair phase does not prevent marking the cluster consolidated. The decisions are recorded in `.scratch/score-based-consolidation/issues/05-pair-moves.md` (Comments).

Score-based consolidation searches in up to two phases sharing one 15-second submission deadline. The producer checks the deadline before submitting each move. Submission can wait for a worker, so moves already submitted or waiting to be submitted may start and finish after the deadline; their results are still used. The deadline does not cancel simulations or impose a hard limit on search duration. A search is reported as timed out only when the producer stops submitting moves after observing expiry; pending work can finish after expiry without setting that flag. The phases and limits come from the earlier implementation and are fixed constants, not settings.

1. **Single-node moves.** The candidates are shuffled, then every one is simulated alone. Shuffling replaces the earlier price-per-workload sort: order only matters when the deadline cuts the search short, and a fixed order would leave the same nodes unevaluated every time.
2. **Pair moves**, only if no single-node move is feasible (saves money and scores above zero) and the deadline was not hit. A pair is admissible only if it passes the budget and pacing check that validation runs before compute. That check depends only on the pair's two NodePools, so it runs once per pool pair and is cached for the pass. All admissible pairs are tried when there are at most 256. Otherwise 256 distinct admissible pairs are sampled, weighting each node by `max(0.05, 1 − CPU utilization)`; inadmissible and repeated draws are redrawn, and sampling stops after 4096 draws. A pair is kept only if it lands on exactly one new node.

The ten best moves by score are kept; the limit only bounds validation work. The method waits out the rest of the validation delay, then validates every kept move in search-score order. Validation is the search repeated on a fresh snapshot: the method snapshots the cluster again, builds candidates for the kept moves' sources, and runs the search's per-move step (compute, score, accept) on one simulator over them. Before compute, every source must still be a candidate, none may be nominated, no pool may have more sources than its budget, and whole-command pacing must admit the move; after compute, nomination is rechecked. A move whose simulation errors is logged and skipped, as in the search. Validation applies the same acceptance rule to every kept move: at most one new node, positive savings, and a positive score. A pair that now lands on no new node is accepted, because both sources still empty for less, and keeps kind `pair`; one that lands on two new nodes fails with `scheduling`. Changed standby destinations and changed replacement launch options are allowed, because everything is re-simulated and priced from the fresh snapshot. The move with the highest positive rescored score is run exactly as rescored. Equal rescored scores retain search order. This accounts for changes in standby cost during the validation delay that can change which move saves the most.

**Batch moves** are grown after validation, on the validation snapshot and simulator. The seeds are up to three moves that passed validation and need no new node, the best by rescored score, and they grow in parallel. Each seed tries the feasible single-node moves from the search that need no new node, in search-score order, leaving out kept moves that failed validation. A proposed batch is first checked against each source pool's `Underutilized` budget and whole-command pacing, and skipped without simulating if it fails. Otherwise it is simulated jointly, and the addition sticks only if the batch still needs no new node, saves money, and scores strictly higher than before. Each seed gets at most 32 joint simulations, a fixed constant chosen with this design, with no time deadline. The move that runs is the highest rescored score among the validated moves and the grown batches. Pacing charges one unit per source node.

Growing after validation means one batch is built from moves known to be valid, on the same fresh snapshot and with the same checks, instead of validating many overlapping batches whose shared nodes make them fail together. A batch must strictly raise the score at each step because the last accepted batch is what runs.

The cluster is marked consolidated only when every eligible single-node move was evaluated, the pair phase (if it ran) finished before the deadline, no move was kept, no simulation failed, and no candidate was lost to budgets or pacing. A sampled pair phase does not prevent marking: the next cluster change or the five-minute refresh brings a new sample, and an idle cluster does not search and log every pass.

Candidates still pass upstream's `consolidateAfter` check. The earlier implementation ignored it, which required changing the upstream NodeClaim controller for a setting operators can already set to `0s`.

## Consequences

The search is one unit that takes the candidates, a simulate function, a random source, and the per-pass baselines, and returns ranked moves. That makes it the test boundary: search rules and the score are tested in plain Go with a fake simulator and hand-computed numbers, which is much faster than envtest. Ginkgo specs only show the controller carrying out a single-node move, a batch move, and a pair move.

## Considered Options

- **Grow batch moves in the search and validate them with the other kept moves.** This was the original decision. Rejected: batch moves outscore single-node moves, so the kept moves fill with overlapping batches that fail validation together. That needed a reserved place for the best single-node move, and every growth simulation was repeated at validation anyway.
- **Also reserve places for the single-node move that overlaps least with the others, and for the smallest batch move**, as the earlier implementation did. Rejected: growing batch moves after validation removes the failure these places guarded against.
- **Validate with upstream's consolidation validator.** Rejected: it rebuilds every candidate in the cluster twice and a fresh simulator for each kept move, and needed a score-based special case to keep the search's launch options.
- **Run the first move that passes validation and reject changed standby destinations.** Rejected: a changed destination can still save money, and rescoring all kept moves can find a better move after the validation delay.
- **Enforce the deadline again when a worker starts a simulation.** Rejected: the submission deadline is sufficient; allowing pending work to finish keeps deadline handling simple and preserves its results.
- **Make the search limits configurable.** Rejected: nothing showed a need, and each setting adds parsing, validation, and documentation.
- **Reject a pair that lands on no new node at validation.** Rejected: both sources still empty without a launch, which is strictly better than the planned pair.
- **Remove the consolidated state from score-based consolidation.** Rejected: pod churn resets it often in busy clusters, but in an idle cluster it avoids a full search and an Info log on every 10-second pass.
