# Move search and selection

Status: accepted

**Amendment (2026-11-16):** During implementation review of ticket 01 (search and selection), the operator approved the selection model in this ADR—validate every kept move, rescore from re-simulation, run the highest positive rescored savings, and allow changed reactivated standby destinations—superseding earlier scratch spec wording that required running the first move that passes validation and rejecting destination changes. The decision is recorded in `.scratch/score-based-consolidation/issues/01-search-and-selection.md` (Comments).

**Amendment (2026-11-17):** Ticket 01_1 (validation from one snapshot) replaced the upstream consolidation validator with the search repeated on a fresh snapshot, and dropped keeping the original replacement launch options. The decision is recorded in `.scratch/score-based-consolidation/issues/01_1-validation-from-one-snapshot.md` (Comments).

**Amendment (2026-11-20):** Ticket 01_2 (pacing before simulation) moved the whole-command pacing check before compute, so a move it rejects costs no simulation. The decision is recorded in `.scratch/score-based-consolidation/issues/01_2-pacing-before-simulation.md` (Comments).

Score-based consolidation searches in up to three phases sharing one 15-second submission deadline. The producer checks the deadline before submitting each move. Submission can wait for a worker, so moves already submitted or waiting to be submitted may start and finish after the deadline; their results are still used. The deadline does not cancel simulations or impose a hard limit on search duration. A search is reported as timed out only when the producer stops submitting moves after observing expiry; pending work can finish after expiry without setting that flag. The phases and limits come from the earlier implementation and are fixed constants, not settings.

1. **Single-node moves.** The candidates are shuffled, then every one is simulated alone. Shuffling replaces the earlier price-per-workload sort: order only matters when the deadline cuts the search short, and a fixed order would leave the same nodes unevaluated every time.
2. **Batch moves**, only if a single-node move was found. Growth starts from the three best single-node moves that need no new node. Other such moves are added one at a time, and each addition is simulated jointly and kept only if the batch still needs no new node. Each starting move gets at most 256 joint simulations. A batch move may not exceed any source pool's `Underutilized` budget or disruption-pacing per-batch cap.
3. **Pair moves**, only if no single-node move saves money and the deadline was not hit. All pairs are tried when there are at most 256. Otherwise 256 distinct pairs are sampled, weighting each node by `max(0.05, 1 − CPU utilization)`. A pair is kept only if it lands on exactly one new node.

The ten best moves by score are kept, plus the best single-node move if it is not among them. Batch moves usually outscore single-node moves, because their terms add up. Without that one reserved place, all ten kept moves could share a node that fails validation, and the pass would be wasted. The method waits out the rest of the validation delay, then validates every kept move in search-score order. Validation is the search repeated on a fresh snapshot: the method snapshots the cluster again, builds candidates for the kept moves' sources, and runs the search's per-move step (compute, score, accept) on one simulator over them. Before compute, every source must still be a candidate, none may be nominated, no pool may have more sources than its budget, and the move must pass whole-command pacing, so a move these checks reject costs no simulation; after compute, nomination is rechecked. A move whose simulation errors is logged and skipped, as in the search. Validation re-applies the move's own acceptance rule: at most one new node and a positive score for single-node moves, and the batch and pair rules for those moves. Changed standby destinations and changed replacement launch options are allowed, because everything is re-simulated and priced from the fresh snapshot. The move with the highest positive rescored score is run exactly as rescored. Equal rescored scores retain search order. This accounts for changes in standby cost during the validation delay that can change which move saves the most. Pacing charges one unit per source node. The cluster is marked consolidated only when every eligible move was evaluated, no move was kept, no simulation failed, and no candidate was lost to budgets or pacing.

Candidates still pass upstream's `consolidateAfter` check. The earlier implementation ignored it, which required changing the upstream NodeClaim controller for a setting operators can already set to `0s`.

## Consequences

The search is one unit that takes the candidates, a simulate function, a random source, and the per-pass baselines, and returns ranked moves. That makes it the test boundary: search rules and the score are tested in plain Go with a fake simulator and hand-computed numbers, which is much faster than envtest. Ginkgo specs only show the controller carrying out a single-node move, a batch move, and a pair move.

## Considered Options

- **Also reserve places for the single-node move that overlaps least with the others, and for the smallest batch move**, as the earlier implementation did. Rejected: one reserved single-node move covers the failure that matters.
- **Validate with upstream's consolidation validator.** Rejected: it rebuilds every candidate in the cluster twice and a fresh simulator for each kept move, and needed a score-based special case to keep the search's launch options.
- **Run the first move that passes validation and reject changed standby destinations.** Rejected: a changed destination can still save money, and rescoring all kept moves can find a better move after the validation delay.
- **Enforce the deadline again when a worker starts a simulation.** Rejected: the submission deadline is sufficient; allowing pending work to finish keeps deadline handling simple and preserves its results.
- **Make the search limits configurable.** Rejected: nothing showed a need, and each setting adds parsing, validation, and documentation.
